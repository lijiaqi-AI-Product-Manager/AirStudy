# 机场搜索排序

## 1. 为什么不走 SQL

`AirportDao.search` 用的是 `LIKE '%x%'`。这条路有三个致命问题：

| # | 问题 | 后果 |
|---:|---|---|
| ① | 前导通配符让索引完全失效 | 每次按键 = 83k 行全表扫。而 `airports` 表**一个索引都没加**（照抄竞品决定）。中端机实测 60~120 ms |
| ② | 每次按键跨进程 | Room 查询走 JNI + Cursor 映射，83k 行的 Cursor 窗口分配成本比计算本身还高 |
| ③ | `LIKE` 对中文逐字节匹配 | `city LIKE '%北京%'` 能中，但用户输拼音 `beijing` 时**一条也中不了** |

→ 结论：**启动后一次性载入内存建索引，之后全在内存搜索。**

### 1.1 内存与耗时实测

| 指标 | 实测值 | 说明 |
|---|---|---|
| 索引构建（83,799 条） | **83 ms** | JVM 单线程。真机约 380~450 ms，必须在 IO 线程、首帧之后 |
| 单次搜索 `PEK` | **2 ms** | |
| 单次搜索 `Beijing` / `Tokyo` | **5~6 ms** | |
| 单次搜索 `Internat`（宽匹配） | **19 ms** | 最坏情况：命中面广 |
| 常驻堆 | **约 8~10 MB** | 索引只存下标，不复制机场对象 |

> **注（R2 修订，2026-10-27）**：正式库按竞品口径只导入 **9,068 条有 IATA 的机场**
> （竞品 `iataCode/icaoCode NOT NULL` 决定了这个池子，见
> `03_reverse/07_逐文件全量审计/01_APK1资产/01_APK1_assets全量审计.md` §2.5）。
> 上表的 83,799 是**全量 CSV 压力上限**，不是线上行数；9,068 条下索引构建与
> 搜索只会更快，但性能断言仍以 83,799 为准，防止将来扩大池子时退化。

> **★ 为什么索引不复制机场对象**
> 83,799 个 `Airport` 对象本身约 30~40 MB。如果索引再持一份，
> 直接翻倍。索引只存 `List` 下标 → `Airport` 由调用方持有，
> `search(query, airports)` 时传回来。
> 代价是「传错列表会越界」—— 所以 `search` 开头有 `require` 明确抛
> `IllegalArgumentException` 而不是让 `IndexOutOfBoundsException` 从内部冒出来。

## 2. 命中层级（`Tier` 枚举顺序即优先级）

| 序 | 层级 | 匹配条件 | 示例 |
|---:|---|---|---|
| 0 | `CODE_EXACT` | `iataCode == q` 或 `icaoCode == q` | `PEK` → 首都机场 |
| 1 | `CODE_PREFIX` | `iataCode / icaoCode` 以 q 开头 | `ZB` → ZBAA/ZBHH/ZSPD… |
| 2 | `NAME_PREFIX` | 英文名以 q 开头 | `Beijing` |
| 3 | `CITY_PREFIX` | 英文城市以 q 开头 | `Tok` → Tokyo |
| 4 | `CHINESE` | 中文名/中文城市 **包含** q | `首都` → 北京首都国际机场 |
| 5 | `PINYIN` | 拼音首字母包含 q，或全拼以 q 开头（**q 至少 2 字符**） | `bj` → 北京 |
| 6 | `NAME_CONTAINS` | 英文名包含 q | `International` |
| 7 | `CITY_CONTAINS` | 英文城市包含 q | `jing` |

### 2.1 三个关键排序决策

**① `CODE_EXACT` 为什么单独一层**
用户输完整三字码时想的是「就是这一个」，不是「所有以它开头的」。
单独成层让 UI 能做特殊渲染（「快捷直达」样式），也让 `PEK` 永远排第一。

**② `CHINESE` 为什么在 `PINYIN` 之前、`NAME_CONTAINS` 之后**
- 排在 `NAME_CONTAINS` 前：中文输入是**最明确的意图**（中文界面输中文），
  比"英文名里恰好含这几个字母"可信得多。
- 排在 `PINYIN` 后：拼音是"中文用户用英文键盘打中文"，与英文名匹配同等可信。
- **中文层内部不区分前缀/包含**：「首都」既不是「北京首都国际机场」的前缀
  也不是后缀，用户心智是"这个词在里面"。硬切两个层级反而让排序不可解释。

**③ 拼音为什么要求 `q.length >= 2`**
单个字母 `b` 能命中北京/巴黎/柏林/波士顿/曼谷…几百条。
拼音本只是"补充手段"，不加这个门槛就变成噪音源，
会把真正的前缀匹配挤到列表后半屏。

### 2.2 返回条数上限

`DEFAULT_LIMIT = 25`。

> 为什么是 25 而不是 20 或 50：竞品的 `byCountry` / `topByPopularity`
> 两条 SQL 都是 `LIMIT 25`，说明它的产品在"一屏能滚到的量"上定的是 25。
> 复刻这个数字的两个实际好处：
> ① 与竞品同关键词、同输入的返回条数一致，截图 diff 时不会因为
>    "多了一条少了一条"而误判；
> ② 25 条 ≈ 用户不需要长滚就能看完，同时不至于短到需要二次翻页。

## 3. 排序的最终比较器

```kotlin
compareBy<Hit> { it.tier.ordinal }          // 层级
    .thenByDescending { it.airport.popularity }  // 热度
    .thenBy { it.airport.displayCode }       // 码字典序（稳定器）
```

> **★★ 第三层 `thenBy { displayCode }` 不是可有可无的**
>
> 没有它，两条「层级相同 + 热度相同」的机场，顺序取决于**列表原始顺序** ——
> 而原始顺序来自 `SELECT * FROM airports`（无 `ORDER BY`）。
> SQLite **不保证**这种查询的行序稳定。
>
> 表现是：同一关键词、同一时刻，刷新两次，两条同分结果互换位置。
> 用户会以为列表在「跳」—— 这是最难排查的一类 bug，
> 因为它不可复现、只在真机上偶发。
>
> `AirportSearchIndexTest` 的 `同层级同热度时按码字典序排，保证结果稳定`
> 就是钉这一条：它故意把 `BBB` 放在列表前面，断言结果仍是 `AAA, BBB`。

## 4. 归一化（三条真实输入）
| 输入 | 处理 | 为什么必须有 |
|---|---|---|
| `Pek` / `pEk` | 转大写 | 基础 |
| `PE K` / ` PEK ` | 去所有空白 | 用户手抖、粘贴带空格 |
| `ＰＥＫ`（U+FF30…） | **全角转半角** | 中文输入法在中文状态直接敲键盘，输出全角。屏幕上看到的是「PEK」，代码里完全不等。**竞品没做这个** |
| `ZB-AA` | 码归一化去掉非字母数字 | 从机票/行程单抄下来常带连字符 |

### 4.1 不做的事

**不做 Unicode 变音符号折叠**（`Zürich` → `zurich`）。
需要 `Normalizer`，单次调用约 2 μs × 83k = 166 ms，而机场名里变音符号不多
（主要是欧洲）。收益远小于成本 —— 且竞品连全角都没处理，不做不算欠债。

**中文归一化不走 `normalize()`**，单独一个 `normalizeZh()`：

> 中文标点「，」（U+FF0C）落在全角 ASCII 区间 `U+FF01..FF5E` 里，
> 会被 `normalize()` 转成半角 `,`。对**用户输入**这是想要的，
> 但机场中文名里的「，」是**数据本身的一部分**。
> 只要查询与索引两边都走 `normalizeZh()`，就天然一致。

## 5. 中英双名的展示规则

见 `AirportNameFormatter`。核心约束：

| 事故 | 防范 |
|---|---|
| 外籍用户看到中文 | `preferChinese` 由调用方按 locale 决定，**不是"哪条有中文用哪条"** |
| 中文界面出现空白机场名 | 降级链 `nameZh → name`，且 `isNotBlank()` 判空（防清洗产出的空串） |
| 中英混排行高跳动 | 同一屏内**用同一个基准**，不按单条有无中文名决定 |

目前中文名覆盖率：`large_airport` 约 700 条、`medium_airport` 约 4,700 条
（M3 内容工程）；`small_airport` 不提供中文名，保持英文。
管道已通（字段 + 索引层 + 展示降级），数据填充是后续工作。

## 6. 机器校验清单

| 断言 | 守的是什么 |
|---|---|
| `四种典型输入都能搜到首都机场` | 规格书 §04 唯一硬验收 |
| `北京命中的是中文城市字段而不是英文名` | 命中来源不漂移 |
| `中文名里的任意连续片段都能命中` | 中文层用 contains 而非前缀 |
| `同层级同热度时按码字典序排，保证结果稳定` | 结果顺序确定 |
| `单个字母不触发拼音匹配` | 拼音不变成噪音源 |
| `八万条数据下单次搜索在一百毫秒内` | 性能防退化 |
| `传入比索引更短的机场列表时立刻抛错而不是越界` | 防误用 |
